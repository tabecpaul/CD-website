# 20분 무료 콜백 일정 확정 자동화 설계

## 1. 목적

검사 콜백 신청이 관리자 CRM에 접수된 뒤 실제 통화 일정을 빠르게 확정하고, 고객이 일정을 잊거나 변경 과정에서 이탈하는 문제를 줄인다.

핵심 여정은 다음과 같다.

`콜백 신청 → 관리자 확인 → 정확한 일시 확정 → 고객 확정 이메일 → 고객 캘린더 추가 → 24시간 전 알림 → 필요 시 변경 요청 → 관리자 재확정`

초기 운영자는 1명이며, 고객이 공개 시간표에서 직접 예약하는 방식은 사용하지 않는다. 관리자가 신청자의 희망 날짜와 시간대를 확인한 뒤 정확한 일시를 지정한다.

## 2. 운영 원칙

- 모든 콜백은 20분이며 시간대는 `Asia/Seoul`로 고정한다.
- 관리자가 정확한 시작 일시를 입력하고 명시적으로 확정해야 고객에게 안내한다.
- 고객에게 Google Calendar 추가 링크와 Apple Calendar·Outlook에서 사용할 수 있는 `.ics` 파일을 제공한다.
- 일정 시작 24시간 전에 알림 이메일을 한 번 발송한다.
- 고객의 변경 요청은 일정을 즉시 바꾸지 않는다. 관리자가 새 일시를 재확정해야 변경이 완료된다.
- Google Calendar API나 외부 예약 서비스는 연결하지 않는다.
- 기존 콜백 신청·CRM·Resend·크론 구조를 확장하고 별도 운영 시스템을 만들지 않는다.

## 3. 상태 모델

일정 상태는 기존 영업 진행 상태와 분리한다.

### 3.1 일정 상태

- `unconfirmed` — 정확한 일정 미확정
- `confirmed` — 고객에게 확정 안내 완료 또는 안내 재시도 가능 상태
- `reschedule_requested` — 고객이 변경을 요청했으나 기존 일정은 아직 유효
- `completed` — 콜백 완료
- `cancelled` — 콜백 취소

기존 CRM 상태는 고객 여정 전체를 나타내고, 일정 상태는 콜백 약속만 나타낸다. 최초 일정 확정 시 CRM 상태가 `new`이면 `scheduled`로 함께 변경한다. 다른 CRM 상태는 일정 처리만으로 되돌리거나 덮어쓰지 않는다.

### 3.2 일정 버전

각 확정에는 1부터 증가하는 `schedule_version`을 부여한다. 일정이 재확정되면 버전을 올리고 이전 버전에 속한 미발송 알림 작업과 변경 요청 링크를 무효화한다.

## 4. 데이터 모델

기존 `assessment_callback_requests`에 다음 필드를 추가한다.

- `schedule_status` varchar, 기본값 `unconfirmed`
- `confirmed_start_at` timestamptz, nullable
- `confirmed_end_at` timestamptz, nullable
- `schedule_version` integer, 기본값 0
- `confirmation_email_status` varchar, nullable
- `confirmation_email_sent_at` timestamptz, nullable
- `confirmation_email_error` varchar, nullable
- `reminder_email_sent_at` timestamptz, nullable
- `reschedule_requested_at` timestamptz, nullable
- `reschedule_preferred_date` date, nullable
- `reschedule_time_slot` varchar, nullable
- `reschedule_message` varchar(500), nullable
- `reschedule_token_hash` varchar, nullable
- `reschedule_token_expires_at` timestamptz, nullable

24시간 전 알림은 새 `callback_schedule_email_jobs` 테이블로 관리한다.

- 요청 ID
- 일정 버전
- 작업 종류: `reminder_24h`
- 예약 시각
- 상태: `pending`, `processing`, `sent`, `failed`, `skipped`
- 시도 횟수, 마지막 안전한 오류 코드
- 발송·생성·수정 시각

`요청 ID + 일정 버전 + 작업 종류`에 고유 제약을 두어 크론이 반복 실행돼도 같은 알림이 중복 생성되거나 발송되지 않게 한다. 테이블은 RLS를 활성화하고 공개 Supabase 정책을 만들지 않는다.

## 5. 관리자 CRM

기존 콜백 상세 화면에 일정 관리 영역을 추가한다.

### 5.1 입력과 동작

- 정확한 날짜
- 시작 시각
- 자동 계산된 종료 시각
- 현재 일정 상태와 이메일 상태
- `일정 확정 및 이메일 발송`
- 확정 후에는 `새 일정으로 재확정`
- 이메일 실패 시 `확정 이메일 재발송`
- 필요 시 `콜백 완료`, `콜백 취소`

브라우저 입력은 한국시간으로 표시하고 서버에서 유효한 `Asia/Seoul` 시각으로 변환한 후 UTC `timestamptz`로 저장한다. 시작 일시는 저장 시점보다 미래여야 하며 종료 일시는 서버가 시작 후 20분으로 계산한다.

### 5.2 일정 충돌

새 일정이 기존의 `confirmed` 또는 `reschedule_requested` 일정과 겹치면 관리자가 확인할 수 있는 경고를 표시한다. 1인 운영에서 예외 대응이 가능하도록 강제 차단하지 않으며, 경고를 확인한 뒤 명시적으로 확정할 수 있다.

### 5.3 확정 처리 순서

1. 관리자 인증과 입력을 검증한다.
2. 일정 충돌 여부를 확인한다.
3. 일정 버전을 올리고 새 일시를 트랜잭션으로 저장한다.
4. 이전 버전의 대기 중 알림을 `skipped`로 변경한다.
5. 새 24시간 전 알림 작업을 생성한다.
6. 새 변경 요청 토큰의 해시와 만료 시각을 저장한다.
7. 확정 이메일을 발송하고 결과를 저장한다.

DB 저장이 성공한 뒤 이메일이 실패하면 일정은 유지한다. 화면에는 발송 실패를 표시하고 관리자가 같은 일정 버전의 이메일만 재발송할 수 있게 한다.

## 6. 고객 확정 이메일과 캘린더

확정 이메일에는 다음을 포함한다.

- 한국어로 표시한 확정 날짜와 시작·종료 시각
- 20분 전화 콜백이라는 설명
- 신청 당시 휴대전화 번호의 일부 마스킹 표시
- Google Calendar 추가 버튼
- Apple Calendar·Outlook용 `.ics` 다운로드 버튼
- 일정 변경 요청 버튼
- 변경 요청만으로 일정이 바뀌지 않으며 재확정 이메일을 받아야 완료된다는 안내

Google Calendar 버튼은 표준 캘린더 URL을 사용하며 외부 API 권한을 요청하지 않는다. `.ics`는 표준 iCalendar 형식으로 생성하고 `Asia/Seoul` 일정, 20분 길이, Career Direct Korea 콜백 제목과 고객 안내만 포함한다. 내부 메모나 인구통계 정보는 캘린더에 넣지 않는다.

캘린더 다운로드와 변경 요청 링크에는 신청 ID, 이메일, 전화번호를 넣지 않는다. 충분히 긴 무작위 토큰을 사용하고 DB에는 토큰 원문 대신 해시만 저장한다.

## 7. 일정 변경 요청

고객은 이메일의 변경 요청 버튼으로 전용 페이지에 접근한다.

입력 항목:

- 새 희망 날짜
- 새 희망 시간대
- 선택 사항인 짧은 메시지, 최대 500자

서버는 토큰 해시, 만료 시각, 일정 버전과 현재 상태를 확인한다. 정상 요청이면 일정 상태를 `reschedule_requested`로 바꾸고 요청 내용을 저장한 뒤 관리자에게 Resend 알림을 보낸다.

변경 요청이 접수되어도 기존 `confirmed_start_at`과 알림 작업은 즉시 삭제하지 않는다. 관리자가 새 일시를 재확정하면 이전 작업을 무효화하고 새 일정과 알림을 만든다. 관리자가 기존 일정을 유지하기로 하면 요청 상태를 해제하고 기존 일정 버전을 유지할 수 있다.

토큰은 해당 콜백 종료 후 24시간까지 유효하게 하되, 재확정·완료·취소 시 이전 버전 토큰은 즉시 무효화한다.

## 8. 24시간 전 알림

새 `/api/cron/callback-reminders` 엔드포인트가 기존 `CRON_SECRET` 인증 방식을 재사용한다. Supabase `pg_cron`과 `pg_net`이 5분마다 엔드포인트를 호출한다.

크론 처리기는 다음 조건을 모두 만족하는 작업만 가져온다.

- 상태가 `pending`
- 예약 시각이 현재보다 이전
- 요청의 일정 상태가 `confirmed` 또는 `reschedule_requested`
- 작업의 일정 버전이 요청의 현재 버전과 일치
- 확정 시작 시각이 아직 미래

동시 실행에서 같은 작업을 잡지 않도록 원자적으로 `processing` 상태를 확보한다. 성공 시 `sent`, 취소·구버전·지난 일정은 `skipped`, 일시적 실패는 제한된 횟수만 재시도한 뒤 `failed`로 기록한다.

일정이 확정 시점 기준 24시간 이내라면 알림 작업은 만들지 않는다. 확정 이메일 자체가 임박 일정 안내 역할을 한다.

## 9. 보안과 개인정보

- 일정 확정·재발송·완료·취소 API는 관리자 세션이 있어야 한다.
- 공개 변경 요청·캘린더 엔드포인트는 고엔트로피 토큰과 일정 버전을 검증한다.
- 토큰 원문, 관리자 세션, 이메일 API 키를 로그에 출력하지 않는다.
- 공개 오류 응답으로 신청 존재 여부나 개인정보를 추론할 수 없게 한다.
- 변경 메시지에는 운영에 필요한 내용만 적도록 안내하고 길이와 문자 입력을 검증한다.
- 고객 이메일과 캘린더에는 운영 메모, 성별, 혼인 여부, 상담 주제를 포함하지 않는다.

## 10. 오류 처리

- 잘못되거나 과거인 일시는 저장하지 않고 항목별 오류를 반환한다.
- 중복 클릭은 같은 일정 버전에 확정 이메일과 알림 작업을 중복 생성하지 않는다.
- 확정 이메일 실패는 일정 저장을 롤백하지 않는다.
- 알림 이메일 실패는 콜백 신청이나 확정 상태를 변경하지 않는다.
- 변조·만료·구버전 링크는 개인정보 없는 안전한 오류 페이지를 표시한다.
- 분석·관리자 알림 실패는 고객의 변경 요청 저장을 취소하지 않는다.
- DB 오류는 성공으로 표시하지 않고 관리자 화면에 재시도 가능한 일반 메시지를 보여준다.

## 11. 분석

개인정보 없는 다음 이벤트를 기존 분석 체계에 추가한다.

- `callback_schedule_confirmed`
- `callback_reschedule_requested`
- `callback_schedule_reconfirmed`
- `callback_reminder_sent`

공개 분석 API는 고객이 임의로 확정·발송 이벤트를 만들 수 없게 하고, 해당 이벤트는 서버 처리 성공 후에만 기록한다. 일정 ID, 이메일, 전화번호는 분석 이벤트에 저장하지 않는다.

## 12. 검증과 출시

### 12.1 자동 검증

- 한국시간 입력의 UTC 저장과 다시 한국시간 표시
- 종료 시각이 시작 후 정확히 20분인지 확인
- 과거 일시와 잘못된 형식 거부
- 일정 충돌 탐지와 관리자 확인 처리
- 일정 버전 증가와 구버전 작업 무효화
- 확정 API 중복 요청의 이메일·작업 중복 방지
- `.ics` 구문, 시작·종료 시각, 파일 헤더 확인
- 변경 토큰의 정상·만료·변조·구버전 처리
- 크론 인증과 24시간 알림의 단일 발송 보장
- 취소·완료·지난 일정의 알림 건너뛰기
- 관리자 인증 없는 변경 API 차단
- TypeScript, ESLint, Next.js 프로덕션 빌드

### 12.2 운영 검증

1. 테스트 콜백 신청을 생성한다.
2. 관리자 상세에서 미래의 정확한 시각을 확정한다.
3. 확정 이메일 수신과 마스킹된 연락처를 확인한다.
4. Google Calendar 링크와 `.ics` 파일의 20분 일정을 확인한다.
5. 고객 변경 요청을 제출하고 CRM 상태와 관리자 알림을 확인한다.
6. 새 일시로 재확정하고 이전 링크·알림 작업이 무효화됐는지 확인한다.
7. 테스트 작업의 예약 시각을 조정해 24시간 알림이 한 번만 발송되는지 확인한다.
8. 관리자 화면에서 완료와 취소 처리를 확인한다.

## 13. 제외 범위

- Google Calendar API OAuth와 운영자 캘린더 자동 생성
- Calendly·Cal.com 등 외부 예약 서비스
- 고객의 공개 시간 슬롯 직접 선택과 즉시 확정
- SMS·카카오 알림톡
- 화상회의 링크 자동 생성
- 다중 상담자 배정과 상담자별 캘린더
- 결제 링크·결제 상태 자동화
