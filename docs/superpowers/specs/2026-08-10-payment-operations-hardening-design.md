# 결제 운영 안정화 설계

## 목적

무통장입금 MVP를 실제 고객 운영에 사용하기 전에 테스트 데이터와 실제 매출을 분리하고, 금전·서비스 상태 변경을 추적하며, 위험 작업의 오조작을 방지한다. 이번 단계는 자동 이메일이나 자동 상태 변경을 추가하지 않고 향후 자동화가 가능한 데이터 기반을 만든다.

## 범위

### 포함

- 테스트 콜백·결제 표시 및 운영 통계 제외
- 결제·증빙·평가·컨설팅·환불 상태 변경 이력
- 위험 작업 확인 단계와 환불 미리보기
- 운영 예외 필터와 경고 배지
- 기존 테스트 건 분류 기능
- 예외 흐름과 통계 분리 검증

### 제외

- 입금기한 자동 취소
- 고객·관리자 자동 독촉
- 이메일 자동 재시도
- 본부 평가 시스템 API 연동
- 자동 입금 조회
- 자동 환불 이체
- SMS·카카오 알림

향후 자동화는 이번 단계에서 저장하는 상태, 기한, 실패 사유와 변경 이력을 기준으로 별도 기능으로 추가한다.

## 핵심 용어

### 평가 링크 발급

Career Direct 본부가 고객 이메일로 평가 링크를 보낸 상태다. 링크 원문은 Career Direct Korea 시스템에 저장하지 않는다.

### 고객 본부 등록

고객이 평가 링크를 열고 Career Direct 본부 시스템에 직접 등록한 상태다. 관리자가 고객을 대신 등록시키는 기능이나 단순 링크 클릭이 아니다.

고객 본부 등록은 평가 크레딧의 상품 포장을 개봉한 것과 같은 사용 개시 시점이다. 이 사실이 확인된 이후에는 평가·보고서 배분액 165,000원이 환불 대상에서 제외된다. 따라서 관리자 화면은 이 단계를 `고객 본부 등록 확인`으로 표현하고, 확인 전 환불 영향 경고를 표시한다.

## 데이터 모델

### 테스트 데이터 표시

`assessment_callback_requests`에 `is_test boolean not null default false`를 추가한다.

- 테스트 표시는 콜백 신청을 기준으로 하며 연결된 결제와 이벤트 집계에 상속된다.
- 테스트 데이터는 관리자 목록과 상세 화면에서 계속 조회할 수 있다.
- 테스트 데이터는 방문·신청·결제·환불·매출 전환 통계에서 제외한다.
- 기존 테스트 신청은 관리자가 상세 화면에서 테스트로 표시할 수 있다.
- 테스트를 실제 고객으로 되돌리는 작업도 운영 이력에 기록한다.

### 운영 이력 테이블

새 테이블 `callback_payment_audit_logs`를 추가한다.

필드:

- `id`
- `callback_request_id`
- `payment_id` nullable
- `action`
- `previous_status` nullable
- `next_status` nullable
- `amount` nullable, 원 단위 정수
- `reason` nullable, 최대 500자
- `created_at`

인덱스:

- `(callback_request_id, created_at)`
- `(payment_id, created_at)`
- `(action, created_at)`

이력은 추가 전용이다. 수정·삭제 UI를 제공하지 않는다. 다음 작업이 성공적으로 저장될 때 이력을 함께 생성한다.

- 테스트 여부 변경
- 입금 안내 생성·재발송·취소
- 입금 확인
- 증빙 요청·발행 상태 변경
- 평가 링크 발급 확인
- 고객 본부 등록 확인
- 평가 시작·완료
- 컨설팅 일정 설정·변경·완료
- 환불 접수·완료

계좌번호, 환불계좌, 사업자등록증, 이메일 원문과 고객 민감정보는 이력에 저장하지 않는다.

## 트랜잭션과 상태 규칙

- 결제 또는 서비스 상태 변경과 운영 이력 insert는 하나의 DB 트랜잭션으로 처리한다.
- 상태 조건이 맞지 않으면 변경과 이력 모두 저장하지 않는다.
- 동일 요청을 재전송해도 상태가 이미 목표 단계라면 중복 이력을 만들지 않는다.
- 상태를 건너뛰거나 역방향으로 변경할 수 없다.
- 운영자가 상태를 정정해야 하는 예외는 별도의 사유 입력이 있는 관리 action으로 처리한다.
- 고객 본부 등록은 `link_issued` 이후에만 확인할 수 있다.
- 고객 본부 등록 확인 전에 평가 비용 환불 제한 경고를 표시한다.

## 관리자 목록

기존 영업 상태 필터와 별도로 다음 운영 필터를 제공한다.

- 실제 고객
- 테스트 데이터
- 입금기한 초과
- 이메일 발송 실패
- 증빙 처리 필요
- 환불 처리 중

목록에는 다음을 표시한다.

- 테스트 배지
- 결제 상태
- 서비스 상태
- 입금기한 초과 배지
- 이메일 실패 배지
- 증빙 처리 필요 배지

테스트 데이터가 선택된 경우 실제 고객 목록과 시각적으로 구분한다.

## 관리자 상세 화면

### 테스트 데이터

- 상세 헤더에 `테스트 데이터` 배지를 표시한다.
- 테스트 여부 전환에는 확인 단계를 둔다.
- 테스트 건의 금전 작업 영역에는 `실제 입금 또는 환불을 수행하지 마세요`를 표시한다.

### 위험 작업 확인

- 입금 확인: 상품명과 결제액을 다시 표시하고 실제 입금 확인 여부를 묻는다.
- 입금 안내 취소: 취소 사유를 요구한다.
- 고객 본부 등록 확인: 고객이 본부 시스템에 직접 등록했는지 체크하고 165,000원 환불 제한을 고지한다.
- 컨설팅 완료: 실제 3시간 제공 여부를 확인한다.
- 환불 접수: 저장 전에 기준액, 차감액, 조정액과 최종액을 표로 보여준다.
- 환불 완료: 실제 이체 완료 체크 후 확정한다.

### 운영 이력

상세 화면 하단에 최신순 또는 시간순으로 다음을 표시한다.

- 작업명
- 이전 → 이후 상태
- 관련 금액
- 민감정보 없는 사유
- 한국시간 기준 변경 시각

## 환불 안전장치

- 환불 `미리보기`는 DB 상태를 변경하거나 이메일을 보내지 않는다.
- 환불 `접수` 시 서버에서 같은 조건으로 금액을 다시 계산한다.
- 조정액이 0이 아니면 운영 사유를 필수로 입력한다.
- 최종 환불액은 0원 초과, 결제액 이하로 제한한다.
- 고객 본부 등록 전·후 경계를 서버가 저장된 등록 시각으로 판단한다.
- 컨설팅 48시간 전후와 노쇼 기준은 저장된 3시간 컨설팅 시작 시각으로 판단한다.
- 환불 완료는 실제 수동 이체 확인 이후에만 가능하다.

## 분석 집계

관리자 분석 쿼리는 `assessment_callback_requests.is_test = false`인 데이터만 결제 퍼널과 매출에 포함한다.

서버 분석 이벤트는 기존 이벤트를 삭제하지 않는다. 콜백 ID가 없는 과거 익명 방문 이벤트는 그대로 유지한다. 결제 이후 단계의 상품·매출·환불 집계는 콜백과 결제 테이블을 기준으로 테스트 여부를 제외한다.

관리자 분석 화면에는 `테스트 데이터 제외` 문구를 표시한다.

## 오류 처리

- 인증 없음: 401
- Origin 불일치: 403
- 입력 오류: 400
- 상태 충돌 또는 중복 처리: 409
- 데이터 없음: 404
- DB·이메일 장애: 503

이메일 실패는 결제 또는 서비스 상태를 되돌리지 않는다. 운영 이력에는 이메일 실패 action과 안전한 오류 코드만 기록한다. 고객 정보나 환경변수는 로그에 남기지 않는다.

## 검증 시나리오

1. 기존 테스트 콜백을 테스트로 표시하면 목록에는 남고 결제·매출 통계에서 제외된다.
2. 테스트 표시를 해제하면 다음 집계부터 실제 데이터로 포함된다.
3. 입금기한 초과, 이메일 실패, 증빙 필요, 환불 중 필터가 정확히 동작한다.
4. 입금 확인을 중복 클릭해도 상태·이력이 한 번만 기록된다.
5. 평가 링크 발급 전 고객 본부 등록 확인은 거부된다.
6. 고객 본부 등록 확인 화면에 165,000원 환불 제한이 표시된다.
7. 고객 본부 등록 전·후 환불 미리보기 금액이 정책과 일치한다.
8. 컨설팅 48시간 전후, 노쇼, 제공자 미제공 환불액이 정책과 일치한다.
9. 환불 미리보기는 DB와 이메일을 변경하지 않는다.
10. 환불 접수·완료와 운영 이력이 원자적으로 저장된다.
11. 테스트 데이터 안내가 실제 입금·환불 오인을 방지한다.
12. 기존 실제 고객과 콜백·결제 데이터가 기본값 `false`로 호환된다.

## 완료 기준

- 테스트 데이터와 실제 고객 데이터가 목록과 분석에서 분리된다.
- 모든 금전·서비스 상태 변경에 추가 전용 운영 이력이 남는다.
- 고객 본부 등록의 의미와 환불 경계가 관리자 화면에 정확히 표시된다.
- 위험 작업에 확인 단계가 있고 환불은 미리보기와 확정으로 분리된다.
- 운영 예외 필터가 실제 DB 상태와 일치한다.
- 타입검사, lint, production build와 검증 시나리오가 통과한다.
